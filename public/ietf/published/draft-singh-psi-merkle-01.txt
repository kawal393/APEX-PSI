             PSI Merkle Commitment Profile (RFC6962-SHA256)
                       draft-singh-psi-merkle-01

Abstract

   This document specifies the Merkle commitment profile used by Proof
   of Stateful Integrity (PSI) receipts.  It adopts the Merkle Tree Hash
   and inclusion proof of RFC 9162 without modification, fixes leaf
   order, and defines how a receipt declares the profile and how a
   verifier obtains and checks an inclusion proof.  A valid proof shows
   only that a leaf was committed under a root; it says nothing about
   the truth or lawfulness of the sealed content.

   This revision replaces the lexicographic ordering and odd-leaf
   duplication of revision 00, which were incompatible with RFC 9162,
   and withdraws all anchoring claims other than OpenTimestamps.

1.  Introduction

   PSI receipts commit each sealed digest as a leaf of a Merkle tree so
   that a third party can check membership without the full ledger.  The
   key words "MUST", "MUST NOT", "SHOULD", and "MAY" in this document
   are to be interpreted as described in BCP 14 [RFC2119] [RFC8174]
   when, and only when, they appear in all capitals, as shown here.

2.  Profile Identifier

   A receipt using this profile MUST carry the member merkle_profile
   with the value RFC6962-SHA256.  Receipts without this member MUST NOT
   be verified under this profile; they were produced under an earlier
   profile and are out of scope.

3.  Tree Construction

   Leaves are the 32-byte PSI leaf digests, ordered by ledger sequence,
   oldest first.  The tree hash is the Merkle Tree Hash of Section 2.1.1
   of [RFC9162] with SHA-256: a leaf hash is SHA-256(0x00 || leaf) and
   an interior node is SHA-256(0x01 || left || right).  The tree for n
   leaves splits at the largest power of two less than n; equivalently,
   an unpaired node is promoted unchanged and is never duplicated.

   A receipt's root is computed over a window of at most 256 leaves
   ending with the receipt's own leaf.  The window is identified by the
   receipt's leaf index and tree size, both returned with the proof.

4.  Inclusion Proof

   An issuer SHOULD offer a keyless resolver returning, for a receipt
   identifier, a JSON object with members leaf, leaf_index, tree_size,
   audit_path (array of lowercase hex digests, bottom-up), root, and
   root_matches_receipt.  The reference resolver is
   https://qhtntebpcribjiwrdtdd.supabase.co/functions/v1/merkle-
   proof?receipt_id=.

   A verifier MUST check the proof with the algorithm of Section 2.1.3.2
   of [RFC9162] and MUST compare the result with the root printed in the
   receipt, not with the resolver's root member.  The verifier needs no
   further contact with the issuer.

5.  Test Vector

   Leaves are SHA-256 of the ASCII strings "a", "b", "c".  For leaf
   index 2 and tree size 3:

   leaf  = 2e7d2c03a9507ae265ecf5b5356885a5
           3393a2029d241394997265a1a25aefc6
   path  = [ad5ca6cddc0b27c6a83e332bf2801176
            9236e6c6a1f786ebf7b5267b37a5bd22]
   root  = cac3d448d4e20a2ad5eae1f500e63c2a
           7f9217cd14572ba7fd22e26dc1ec2648

6.  Security Considerations

   Inclusion shows commitment, not creation time; time is bounded only
   by an external anchor.  A window shorter than the full ledger means
   two receipts may commit to different roots; each root is checked
   against its own receipt.  An issuer that controls the ledger can
   refuse to issue proofs; receipts already held remain verifiable from
   their own fields.
