# Set the Ed25519 signing seed — the last thing between APEX PSI and a hosted seal

Dated 2026-11-20. Written from outside the project, from measured HTTP answers, not from the repo.

**Done when:** `POST /functions/v1/commit-action` answers 200 with a receipt instead of
`503 {"error":"Signing unavailable; nothing was recorded. Please retry."}`, and the hosted
MCP door's `seal` tool mints a receipt that `GET /functions/v1/verify-hash?hash=…` then
finds. Both are re-measured by the laptop agent from the public internet; nothing here needs
a human to log in and look.

## What is broken, measured 20 Nov

Every hosted **write** in the product is refusing. Read paths are fine.

| endpoint | today's measured answer | |
|---|---|---|
| `POST /functions/v1/notarize` | `500 {"error":"Internal server error"}` | the web "seal this" button |
| `POST /functions/v1/notarize-batch` | `500 {"error":"Internal server error"}` | batch sealing |
| `POST /functions/v1/authorize` | `500 {"error":"Internal server error"}` | permission slips |
| `POST /functions/v1/commit-action` | `503 {"error":"Signing unavailable; nothing was recorded. Please retry."}` | **this one names the reason** |
| `POST /functions/v1/apex-psi-mcp` `seal` | `500` passed through from `/notarize` | the new token-free door |
| `GET /functions/v1/verify-hash?hash=44521bc…` | `200 found=true verified=true` | reads fine |
| `GET /functions/v1/ledger-stats` | `200 total_receipts=6019` | reads fine |
| `GET /functions/v1/trust-anchor` | `200` | reads fine |

`commit-action` is the diagnostic because it catches the signing failure and says so, while the
other three let it fall into a generic 500. So this is one fault, not four.

## The cause, with the numbers

`psi_core.ts` `institutionalSigningSeed()` reads exactly one secret, `APEX_PSI_ED25519_SEED`,
and since `6f2e25a` (19 Nov) `signEd25519Strict` also refuses to sign under a public key the
published trust anchor does not list. That is fail-closed by design: a receipt nobody can
verify is worse than no receipt.

The value currently in this project's secrets derives

```
39a405177480…   ← not in the anchor's keys[]  →  signing refuses, every write 500/503
```

The value the laptop vault holds derives

```
111284cd6462a1eeeae71f58d68745e75a7c3de7a69b7328d5953af1fe840e46   = apex-psi-2026-11
```

Confirmed on the laptop with `node scripts/derive-anchor-key.mjs --check 111284cd…` →
`MATCH: that key is the ledger key for this seed.` The seed itself is never printed.

`apex-psi-2026-11` is already published in the live anchor as `status: "pending"`, and both
shipped verifiers already try it (`packages/psi-verifier/src/index.ts:134`,
`packages/psi-verifier-py/psi_verifier/__init__.py:1097`). So a receipt signed with it verifies
for a stranger **today** — there is no blind window, which is why `33d9a1a` published the key
before letting it sign.

The post-quantum secret is **not** part of this fault: `/pqc-sign` publishes
`9a6bdab92234…`, which is not what its own hardcoded `"psi-fallback"` string derives
(`b3e568fce97f…`), so a real `APEX_PSI_SIGNING_SEED` / `APEX_LATTICE_KEY` is present on this
deployment and `signMlDsa65Strict` will sign once Ed25519 does.

## Do this

1. Set one edge-function secret on project `qhtntebpcribjiwrdtdd` —
   `APEX_PSI_ED25519_SEED` — to the value the operator supplies. The correct value is the one
   already in the laptop's own vault (`C:\Users\apex1\.apex-vault\credentials.env`, same name).
   It must arrive by pasting it into this workspace or into Supabase's secret field: never into
   a GitHub issue, a commit, a workflow log, or this brief.
2. Nothing else. Setting a secret restarts the functions, and that alone activates the new key.
3. Check `/commit-action`: it must answer 200 with a `commit_id`. If it answers 503 again, the
   value that arrived is wrong — stop and say so rather than trying a second one.

## Do NOT

- **Do not redeploy `notarize`, `notarize-batch`, `psi-api`, `commit-action`, `authorize`.**
  `roadmap.md` line 100 says the same while the seed is wrong; a redeploy changes nothing about
  a missing secret and puts the blast radius at five functions instead of zero.
- Do not touch `supabase/functions/apex-psi-mcp/`. It is live and correct: `initialize` 200 with
  `serverInfo.name = apex-psi-mcp`, `tools/list` = exactly `anchor, cite, seal, verify,
  verify_chain`, `GET` → 405 `-32601`, `OPTIONS` → 204 with `Access-Control-Allow-Origin: *`, and
  `verify`/`anchor`/`cite` already return real ledger data to an anonymous caller.
- Do not change `active_key_id` in the anchor, or mark any key rotated. Flipping
  `apex-psi-2026` → `apex-psi-2026-11` is the *next* step, and only once signing answers 200;
  it is the laptop agent's step, not this one.
- Do not add a third Ed25519 key, and do not restate the anchor document anywhere. The anchor has
  one source of truth, the published file; `/trust-anchor` only proxies it.
